# 第 01 章　需求分析：把題目讀成規格

> 需求分析的產出不是「我懂了」，而是**一份別人能拿來驗收、自己能拿來寫測試的清單**。

## 1.1 題目摘要

某連鎖診所有 8 間分院，每間 2 台疫苗冷藏櫃，每台裝一支 IoT 溫度計，每分鐘回報一次溫度。
網路斷線時溫度計先把資料存在本機，恢復後補傳。系統需要：

- 接收批次上傳的量測資料（可重送、72 小時前的資料拒收）
- 支援更換溫度計
- 判定「溫度異常」（連續超出 2–8°C 達 10 分鐘以上）與「斷線」（超過 15 分鐘沒有資料）
- 發通知（寫入紀錄並即時推播，同一事件同種通知只發一次）
- 即時儀表板、24 小時溫度圖表、事件處置、月報與 CSV 匯出
- 一個可以模擬 16 台溫度計、4 種情境的模擬器

技術限制：TypeScript strict、Node 22+、Fastify 或 Express、WebSocket、SQLite（需 migration）、
React 18+ 與 Vite、時鐘必須可注入、使用 Vitest。附 14 條驗收標準。

## 1.2 讀題的方法：名詞、動詞、數字、形容詞

拿到一份文字題目，先用四種顏色的筆劃線：

| 劃什麼           | 會變成什麼               | 本題的例子                                          |
| ---------------- | ------------------------ | --------------------------------------------------- |
| **名詞**         | 實體、資料表             | 分院、冷藏櫃、溫度計、量測、事件、通知、處置、月報  |
| **動詞**         | 用例、API                | 上傳、補傳、更換、判定、通知、處置、匯出            |
| **數字**         | 業務規則、常數、邊界測試 | 2–8°C、10 分鐘、15 分鐘、72 小時、每分鐘一筆、16 台 |
| **形容詞／副詞** | 非功能需求               | 「即時」、「只發一次」、「不亂碼」、「1 秒內」      |

數字最值得花時間。**每一個數字都至少產生兩個測試**：剛好等於邊界、超過邊界一點點。
例如「10 分鐘」→ 9 分鐘不成立、10 分鐘成立；「72 小時」→ 剛好 72 小時接受、75 小時拒收。

## 1.4 非功能需求

| 類別         | 需求                                      | 為什麼重要                                               |
| ------------ | ----------------------------------------- | -------------------------------------------------------- |
| **正確性**   | 度分鐘、合規率要與手算一致                | 度分鐘是判斷疫苗是否報廢的依據，算錯就是錢與病人安全     |
| **冪等性**   | 重送、補傳、亂序不改變最終結果            | IoT 網路不可靠，重送是常態而非例外                       |
| **即時性**   | 狀態變化即時推播；1,440 點圖表 1 秒內繪製 | 異常要盡快被看到                                         |
| **可測試性** | 時鐘可注入                                | 「等 15 分鐘」「斷線 2 小時」無法在測試裡真的等          |
| **可維運性** | 資料庫要有 migration                      | 上線後 schema 一定會改（本專案真的改過一次，見第 10 章） |
| **稽核性**   | 原始量測、處置紀錄不可被覆寫              | 疫苗冷鏈有法遵要求                                       |
| **易用性**   | CSV 用 Excel 直接開啟中文不亂碼           | 使用者是診所人員，不是工程師                             |

## 1.5 隱含需求：題目沒寫，但你一定要回答

這是需求分析最有價值的部分。以下每一題，**如果不在設計階段回答，就會在寫程式時被迫用直覺決定**，
而且不同模組可能做出互相矛盾的決定。

| 問題                                                 | 為什麼不能跳過                                       | 本專案的決定                                               |
| ---------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| 2.0°C 與 8.0°C 算超標嗎？                            | 「超出 2–8°C」可以有兩種讀法                         | 邊界值算正常（範圍是閉區間）                               |
| 「連續 10 分鐘」怎麼量？第 1 筆到第 10 筆只隔 9 分鐘 | 決定第 10 筆還是第 11 筆時成立                       | 每筆讀值代表 1 分鐘：持續時間 = 最後一筆 + 1 分鐘 − 第一筆 |
| 超標期間掉了 1、2 筆資料，還算連續嗎？               | 掉一筆就切斷 → 漏報；永不切斷 → 把無關的兩段黏在一起 | 缺口 ≤ 2 分鐘仍視為連續（設計文件 §5.2 列了三個方案）      |
| 斷線的「開始時間」是什麼？                           | 偵測時間比實際中斷晚了 15 分鐘                       | 最後一筆讀值 + 1 分鐘；偵測時間另外記錄                    |
| 補傳的資料裡有超標怎麼辦？                           | 斷線當下不知道溫度                                   | 補傳後重新判定，產生異常事件並與斷線事件互相關聯           |
| 補傳讓兩段超標連起來了怎麼辦？                       | 原本是兩個事件                                       | 合併成一個，被合併者標記 MERGED（不刪除，保留稽核軌跡）    |
| 舊溫度計在更換**後**才補傳更換**前**的資料？         | 資料屬於哪一台冷藏櫃                                 | 依**量測時間**查當時的綁定，而不是依接收時間               |
| 「月」是哪個時區的月？                               | 10/1 00:00 台灣時間 = 9/30 16:00 UTC                 | 以台灣時間（UTC+8）切分月份                                |
| 合規率的分母是什麼？                                 | 斷線的時間算合規還是不合規？                         | 分母為「有資料的分鐘數」；資料缺漏由完整率反映             |
| 同一事件會發幾則通知？                               | 「只發一次」指的是哪一種？                           | 每個事件每種通知（成立、結束、斷線）各一則                 |

> **教學重點**：隱含需求要**寫下來並讓需求方確認**。本專案在設計文件 §19 列出 7 個待確認事項，
> 全部確認後才開始寫程式。

## 1.6 假設事項：寫下來，並且防禦它

本專案在 README 寫了幾個假設，例如「溫度計的流水號不會歸零」。

這裡有一個重要的教訓（第 10 章會完整說明）：外部 review 指出，
**韌體重開機後用新流水號重送本機緩衝**是現場常見的錯誤。原本的冪等只靠「裝置＋流水號」，
所以同一分鐘的資料會被寫入兩次，度分鐘也跟著加倍。

假設事項有兩種處理方式：

1. **寫在文件裡**：違反時系統行為未定義。
2. **寫在文件裡，並且在系統邊界加上檢查**：違反時系統仍然正確。

對於「違反時會造成錯誤結論」的假設（例如度分鐘），應該選第 2 種。

## 1.7 驗收標準改寫成可執行的規格

驗收標準通常是一句話，要先改寫成 **Given / When / Then**，才能直接變成測試：

> **驗收 #4**：超標 9 分鐘不產生事件；超標 10 分鐘產生事件。

```text
Given  冷藏櫃 C01 第 0 分鐘 5.0°C
When   第 1–9 分鐘每分鐘一筆 9.0°C，第 10 分鐘 5.0°C
Then   沒有溫度異常事件，沒有通知

Given  冷藏櫃 C01 第 0 分鐘 5.0°C
When   第 1–10 分鐘每分鐘一筆 9.0°C
Then   產生一個進行中事件，開始時間 = 第 1 分鐘，持續 10 分鐘，發出一則「成立」通知
```

對應的測試（`apps/server/src/modules/events/excursion-reconciler.test.ts`）：

```ts
it('即時資料：第 10 分鐘成立、回到範圍時結束，各一則通知', () => {
  sendRealtime([5, ...repeat(9, 9)], 0, 1);
  expect(excursions()).toHaveLength(0);

  sendRealtime([9], 10, 11);
  expect(excursions()).toMatchObject([{ status: 'OPEN', started_at: at(1), backfilled: 0 }]);
  // ...
});
```

> **驗收 #5**：累積超標度分鐘與手算一致。

先**自己手算一個例子**放進設計文件，再寫成測試。手算例子是需求方與開發者之間最好的溝通工具：

```text
讀值：8.5, 9.0, 9.5, 10.0, 10.0, 9.5, 9.0, 8.5, 8.2, 8.1
超出：0.5 + 1.0 + 1.5 + 2.0 + 2.0 + 1.5 + 1.0 + 0.5 + 0.2 + 0.1 = 10.3 度分鐘
```

## 1.8 容量估算（Back-of-the-envelope）

在選資料庫之前先算數量級，避免過度設計或設計不足：

| 項目               | 計算               | 結果                                      |
| ------------------ | ------------------ | ----------------------------------------- |
| 每日讀值           | 16 台 × 1,440 分鐘 | 23,040 筆                                 |
| 保存 2 年          | 23,040 × 730       | 約 1,680 萬筆                             |
| 每筆大小（含索引） | 約 100 bytes       | 約 1.5–2 GB                               |
| 單台補傳上限       | 72 小時 × 60       | 4,320 筆 → 單批上限設 1,000，由裝置分批送 |
| 寫入速率           | 16 筆／分鐘        | 極低，單機 SQLite 綽綽有餘                |
| 24 小時圖表        | 1,440 點           | Canvas 繪製毫秒級                         |

結論：**這不是大數據問題，而是正確性問題**。這個判斷直接影響第 04 章的技術選型：
不需要時序資料庫、訊息佇列或分散式架構，應該把精力放在判定邏輯的正確性。
