# 第 10 章　檢討與練習：從找到的缺陷中學習

> 一個專案最有價值的教材，往往不是它做對的地方，而是**它做錯、後來被發現、然後修正**的地方。
> 本章整理開發過程與交付後被發現的所有缺陷，分析它們為什麼能通過原本的測試。

## 10.1 外部 code review 找到的三個問題

交付後，一位外部 reviewer 讀完程式碼並實際寫測試驗證，提出三個修改點（依影響排序）。

### 問題 1：同一時間點換流水號重送，度分鐘被重複計算

**症狀**：送 12 分鐘、每分鐘 9.0°C 的資料，再用**新流水號**重送同樣的 14 個時間點。
回應是「接受 14、重複 0」，讀值從 14 筆變成 28 筆，累積超標度分鐘從 12.0 變成 24.0。

**根因**：冪等只靠 `PRIMARY KEY (device_id, seq)`。README 寫了「假設流水號不會歸零」，
但**韌體重開機後用新流水號重送本機緩衝**是現場常見的錯誤。

**為什麼測試沒抓到**：所有重送測試都是「同一批資料原封不動重送」，流水號相同。
測試是根據**自己的假設**寫的，所以永遠不會挑戰這個假設。

**修正**（commit `6ac4cbb`）：

1. Migration v2：`(cabinet_id, measured_at)` 加上唯一索引。既有資料若已有重複，先刪除較晚收到的那筆，
   否則建立唯一索引會失敗。這是「上線後才加約束」必須面對的問題。
2. 接收時，被唯一索引擋下的資料計為「重複」；溫度與原紀錄不同時列入衝突並記錄 log，**不覆寫原始紀錄**。
3. 確認月報不受影響：月報原本就用 `COUNT(DISTINCT 分鐘)`，所以比率沒有被灌高，只有度分鐘受影響。

**教訓**：

- **冪等的鍵要用業務意義來定義**。技術上「同一筆」是 `(裝置, 流水號)`，
  但對度分鐘來說，真正的「同一筆」是「同一冷藏櫃、同一分鐘」。
- **會造成錯誤結論的假設，要在系統邊界加上防禦**（第 01 章 1.6 節）。

### 問題 2：伺服器自己停機，被當成所有溫度計斷線

**症狀**（靜態推論，再寫測試確認）：診所電腦更新 Windows 後重開機，停機超過 15 分鐘。
重啟的瞬間，16 台冷藏櫃同時產生斷線事件與 16 則通知，直到溫度計補傳才變成「已補齊」。

**根因**：斷線條件只看「現在 − 最後量測時間」，沒有考慮**監控者自己**不在線的時間。

**為什麼測試沒抓到**：測試中的 `FixedClock` 從來沒有「伺服器重啟」這個概念，每個測試都假設伺服器一直在跑。
設計文件甚至把這個行為列為「已知限制」，認為「從伺服器的角度確實沒收到資料」。

**修正**（commit `865c4f8`）：

```ts
const silentSince = Math.max(lastSeen ?? binding.boundFrom, this.monitoringSince);
```

`monitoringSince` 是服務啟動時間。重啟後先給 15 分鐘寬限；寬限後仍沒資料才成立事件，
而事件的**開始時間**仍是資料真正中斷的時間（第 07 章 7.2 節）。

**教訓**：

- **「沒收到」不等於「對方沒送」**。任何以「沒收到」做判斷的邏輯，都要先問：我自己有沒有在聽？
- 寫在「已知限制」裡的東西，值得再問一次：這真的是不可避免的嗎？還是只是還沒想到解法？

### 問題 3：缺少 LICENSE，前端打包偏大

**LICENSE**：公開的 repo 沒有授權條款，法律上預設「保留所有權利」，別人不能合法地使用或修改。補上 MIT。

**打包大小**：883 kB（gzip 288 kB）。reviewer 推測原因是「ECharts 整包引入」，建議改用 `echarts/core`。

## 10.2 Review 也可能是錯的：先驗證再動手

檢查程式碼後發現，`TemperatureChart.tsx` **早就是**用 `echarts/core` 按需引入。直接照建議改，會發現沒東西可改。

於是用 sourcemap 把打包內容逐一對應回來源套件：

```text
  370 kB echarts       ← 即使按需引入，7 個元件仍需要這麼多
  170 kB zrender       ← ECharts 的繪圖引擎
  126 kB react-dom
   81 kB zod           ← 只有處置表單用到，卻在首屏
   37 kB react-router
   ...
```

真正的問題不是「引入太多」，而是「**所有東西都在首屏**」。修正方式改為路由與圖表的按需載入
（commit `3f6ab27`，第 08 章 8.7 節），首屏從 883 kB 降到約 315 kB。

**教訓**：

- review 意見要**驗證症狀，也要驗證原因**。症狀（883 kB）是對的，原因推測是錯的。
- **優化前先量測**。沒有量測，就只是在猜。

## 10.3 寫這份教材時才發現的漏洞

第 06 章 6.7 節：對帳只檢查「每個成立的 run 都有對應的事件」，沒有檢查「每個事件都還有對應的成立 run」。
當補傳的**正常讀值**填進一個 ≤ 2 分鐘的缺口，把一個 13 分鐘的事件切成兩段 6 分鐘時，
事件不會被撤銷，資料庫與「判定結果 = f(資料)」的原則不一致。

這個問題是在推導「為什麼對帳演算法是正確的」時發現的：寫下「每個既有事件恰好對應一個 run」這句話時，
才意識到它只有在 run **成立**時才對。

**教訓**：

- **把正確性的理由寫成文字**，是找出漏洞最便宜的方法。寫教材、寫設計文件、向別人解釋，都有同樣的效果。
- **對帳要雙向**。只做單向對帳，系統只能處理「變多、變長」，處理不了「變少、變短」。
- **修正需要需求決策**：已經發出的通知、已經填寫的處置紀錄怎麼辦？這不是工程師能單獨決定的。

目前程式碼**尚未修正**這個問題（見練習 C-1）。

## 10.4 開發過程中的其他缺陷

| 缺陷                                         | 發現方式          | 根因類型                                         |
| -------------------------------------------- | ----------------- | ------------------------------------------------ |
| 從未回報的冷藏櫃在第 14 分鐘就判定斷線       | 自我 code review  | `null` 分支的規則與主規則不一致                  |
| CSV 月份 `2026-10` 被 Excel 顯示為「Oct-26」 | 用 Excel 實際開啟 | 只驗證格式，沒有在使用者的工具中驗證             |
| 範例資料的斷線長度多算 4 分鐘                | 檢查畫面與資料庫  | 範例資料以批次送出，第一筆即時資料被併入補傳批次 |
| 範例資料的完整率只有 87%                     | 檢查月報          | 綁定起點比資料起點早一天                         |

把根因歸類後，可以看到模式：**邊界情境（null、時區、工具差異）**與**沒有在真實環境驗證**是兩大來源。

## 10.5 設計反思

### 做得好的地方

1. **判定 = f(資料)**：補傳、重送、亂序、合併全部由同一個機制處理，沒有任何「補傳模式」的特殊分支。
2. **冪等由資料庫約束保證**：問題 1 的修正只需要加一個約束，所有寫入路徑自動受到保護。
3. **可注入時鐘**：所有時間邏輯都能精確測試，也能加速展示。
4. **範例資料走正式流程**：範例事件與規則永遠一致，seed 本身就是一個大型整合測試。
5. **每個數字都有邊界測試**：9/10 分鐘、15 分鐘 ± 30 秒、72/75 小時、2.0/8.0°C。

### 如果重來一次

| 項目                           | 會怎麼做                                                               |
| ------------------------------ | ---------------------------------------------------------------------- |
| 測試資料的產生方式             | 加入屬性測試（隨機分批、隨機亂序、隨機缺口），與「一次送完」的結果比對 |
| 假設事項                       | 每一條假設都問：「違反時會造成錯誤結論嗎？」會的話，加上防禦與測試     |
| 共用套件的入口                 | 一開始就用 subpath exports，避免 zod 進入首屏                          |
| 容忍缺口                       | 做成設定值，讓診所依網路狀況調整                                       |
| 「同時只有一個進行中斷線事件」 | 用 partial unique index 在資料庫層保證，而不是應用層檢查               |
| 圖表套件                       | 認真評估 uPlot，用自己寫參考帶的成本換取 500 kB                        |

## 10.6 練習題

### A 級：理解

- **A-1** 用自己的話解釋為什麼 `detectExcursionRuns` 第一行要排序，並舉一個不排序就會出錯的例子。
- **A-2** 斷線事件的「開始時間」和「偵測時間」為什麼要分開記錄？各自給誰看？
- **A-3** 畫出驗收 #8（斷線 2 小時、補傳含 30 分鐘超標）的時序圖，標出每個 WebSocket 訊息。
- **A-4** 解釋為什麼 `node:sqlite` 的同步 API 讓批次之間不需要鎖。

### B 級：修改

- **B-1** 把「容忍缺口 2 分鐘」改成環境變數 `MAX_CONTINUOUS_GAP_MIN`。注意：偵測、覆蓋率、圖表缺口三處必須一致，前端要怎麼知道這個值？
- **B-2** 新增「電池電量低於 20%」通知，每台溫度計每天最多一則。設計資料表約束來保證「每天最多一則」。
- **B-3** 用 SQLite 的 partial unique index 保證「同一冷藏櫃同時最多一個進行中的斷線事件」，寫 migration v3 與測試。
- **B-4** 把 `@coldtrace/shared` 改成 subpath exports，讓首屏不包含 zod。用 build 結果驗證。

### C 級：設計

- **C-1** 修正第 06 章 6.7 節的漏洞。交付物：
  1. 一份需求提案：被資料推翻的事件要如何呈現？已發出的通知與處置紀錄怎麼辦？要不要發「撤銷」通知？
  2. 失敗的整合測試
  3. 修正（提示：對帳時找出「視窗內、沒有對應到任何成立 run」的既有事件）
  4. 確認斷線事件的關聯（`event_links`）也被正確更新
- **C-2** 設計屬性測試：隨機產生 200 分鐘的讀值、隨機切成 1–20 批、隨機打亂批次順序與批內順序，
  驗證最終事件與一次送完相同。執行 1,000 次，它能找到 C-1 的漏洞嗎？如果不能，要怎麼調整產生器？
- **C-3** 規模擴大到 500 間分院、每 10 秒一筆，並需要多個後端行程。重新設計第 03 章 3.2 節的六個原則，
  說明哪些保留、哪些改變，以及新的並行控制方式。
- **C-4** 目前斷線判定只有「伺服器重啟寬限」。設計一個方案，讓伺服器停機前就已斷線的冷藏櫃不必多等 15 分鐘
  （提示：伺服器能否記錄自己的心跳？）。

## 10.7 帶走的檢查清單

開始你的下一個專案時，可以用這份清單檢查：

- [ ] 題目中的每個數字都有「邊界上」與「邊界外」兩個測試
- [ ] 隱含需求已列出並取得確認
- [ ] 每條假設都評估過「違反時的後果」，嚴重的有防禦
- [ ] 業務邏輯中沒有直接取得現在時間
- [ ] 冪等的唯一鍵依業務意義定義，並由資料庫約束保證
- [ ] 推播或對外通知在 transaction commit 之後
- [ ] 對帳／同步邏輯是雙向的
- [ ] 「沒收到」的判斷有考慮自己是否在線
- [ ] 交付物在使用者的工具中驗證過（Excel、瀏覽器、手機）
- [ ] 優化前有量測，review 意見有驗證
